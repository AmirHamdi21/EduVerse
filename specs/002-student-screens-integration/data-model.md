# Domain Modeling & Integration: Student Screens

## UI-Layer Entities

The Phase 2 integration strictly operates as a read-only consumer of the unified repository generated in Phase 1. 

### `CourseEnrollmentModel` (Consumer Context)
The primary data payload provided by `CoursesBloc` representing a student's enrolled courses. It encapsulates the underlying `CourseModel`.

**Key Display Mappings:**
- **Tile Header**: `course.title`, `course.courseCode` 
- **Metadata**: Instructor Name (`course.instructor.name` or fallback), Credit Hours (`course.creditHours`)
- **Status Badges**: Maps `role` (e.g. `UserRole.student`) and potentially backend statistics for completion rate.
- **Imagery**: `course.thumbnailUrl` -> Network Image (with initials fallback logic generated directly in the widget).

### `CoursesState` Mappings
| State Class | UI Action |
|-------------|-----------|
| `CoursesInitial` | Show blank skeleton cards or initial splash loading widget. |
| `CoursesLoading` | If `cachedEnrollments` exists, display data alongside a subtle refresh indicator. If null, display skeleton loader cards. |
| `CoursesLoaded` | Inject `enrollments` payload into the main `courses_list_view.dart`. Trigger rebuild. |
| `CoursesError` | Display friendly empty/error state illustrations. If `cachedEnrollments` exist, show Snackbar (Offline/Failed cache mode) and keep showing cached list. |

## Internal Logic State
- **Filter State**: Handled natively within the widgets (e.g. `course_filter_bar.dart` maintains a state variable) acting purely on the list generated by the active `CoursesLoaded` state without invoking external repositories.
