Yes, the backend already supports “return to pool / unassign from section” by sending:

```json
{ "draftSectionId": null }
```

to:

```text
PATCH /exams/drafts/:draftId/items/:itemId
```

Evidence:
- The update endpoint exists in [exams.controller.ts](<D:\Graduation\backend\last_backend\EduVerse_Backend\src\modules\exams\exams.controller.ts:349>).
- `UpdateDraftItemDto` allows `draftSectionId?: number | null` in [generate-exam.dto.ts](<D:\Graduation\backend\last_backend\EduVerse_Backend\src\modules\exams\dto\generate-exam.dto.ts:250>).
- The service explicitly handles null and clears the section in [exams.service.ts](<D:\Graduation\backend\last_backend\EduVerse_Backend\src\modules\exams\exams.service.ts:1339>):
  - if section id is a number, it validates the section and assigns it.
  - if `draftSectionId === null`, it sets `item.draftSectionId = null`.
- The database/entity also supports this: `draft_section_id` is nullable, and the relation uses `onDelete: 'SET NULL'` in [exam-draft-item.entity.ts](<D:\Graduation\backend\last_backend\EduVerse_Backend\src\modules\exams\entities\exam-draft-item.entity.ts:28>).

The current blocker is on the Flutter client side, not the backend. In [exam_generator_service.dart](<D:\Graduation\EduVerse\edu_verse\lib\services\api\exam_generator_service.dart:470>), the request only includes `draftSectionId` when it is not null:

```dart
if (draftSectionId != null) 'draftSectionId': draftSectionId,
```

So when the app calls `moveItemsToSection(..., null)`, the field is omitted entirely. The backend receives “no section change” instead of “clear the section.”

Best UX name: use **Unassign** or **Return to pool**. Technically, the app should send an explicit JSON null for that action, then refresh the draft so the question leaves the section card and appears again in the unassigned draft question pool.

2. **Saved exam record**
   This is the saved snapshot: `/exams/:examId`.
   Its lifecycle status can still be `draft`, meaning “saved exam not published yet,” not “editable draft workspace.”

So after save, the backend likely has both:
- finalized draft: `ExamDraftStatus.finalized`
- saved exam: `ExamStatus.draft`

The confusion comes because the UI still lets the instructor open the **finalized draft record** in the draft details screen.
